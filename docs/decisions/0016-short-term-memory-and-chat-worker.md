# 0016: Short-term memory, the basic profile and the chat worker

- Status: proposed with SAV-18; it takes effect when SAV-18's pull request is merged. The open questions below are for Muhammed.
- Date: 2026-11-21, updated 2026-11-22 after review rounds 1 and 2 (points 5 to 8)
- Ticket: SAV-18

## Context

ARCHITECTURE §3.7 says short-term memory holds the last ~20 messages and the **working set** (the last numbered results and the filters that produced them) in Redis for about 24 hours, so "the second one", "show more" and "only the cheap ones" refine the last search. SAV-18 also adds a basic profile (home area, language) and stores messages in `conversation_msg`.

The owner update of 20 Nov 2026 on SAV-18 (record 0015, Q2, Q5 and Q9) moved the chat worker here: ingestion already queues `answer_chat_message` jobs, but nothing ran them. Record 0015 fixed the agent's contract: the working set is passed in (`AgentTurn.working_set`) and returned (`AgentAnswer.working_set`); the worker sets `deletion_confirmed` only for the "Yes, delete" payload; every new store joins `UserDataEraser`.

## Decision

1. **Three Redis keys per user** (`app/memory/session.py`), `savely:memory:<user id>:history|working_set|replies`. Every write restarts the lifetime of all three (`SESSION_TTL_SECONDS`, 86400 in `.env.example`), so a session ends a day after the last exchange. The history is a list appended and trimmed to `SESSION_HISTORY_MESSAGES` (20) in one transaction, so two answers that end together keep both exchanges; the working set is replaced whole.
2. **The working set carries the searches.** `AgentAnswer.working_set` stays the ordered ids. Two additive fields carry the rest of §3.7's "filters that produced it": the tools report each search's tool and checked arguments (`ToolOutcome.search`, `SearchUsed`), the agent returns them as `AgentAnswer.searches`, and the worker passes them back with how many results were shown (`AgentTurn.working_set_searches`, `AgentTurn.working_set_shown`). The model sees the numbered list, which results were not shown yet, and the searches; to narrow, it repeats the search with one more filter, so "only the cheap ones" gets the same filters plus `price`. A turn that lists items without searching ("show more") keeps the earlier searches. An answer that lists no items keeps the last working set, so "thanks" doesn't lose it.
3. **The basic profile is the `user` row.** A new tool, `set_profile(home_area?, country?)`, keeps where the user lives and their ISO country code when they tell it; a country given mid-turn is used by the rest of that turn. The home area is shown to the model on every turn ("near home" needs no question). The model asks once when a question needs a value it doesn't know. `user.language` is the language of the user's last message (the answer's BCP 47 tag), stored by the worker; the save confirmations already read it.
4. **The chat worker** (`app/agent/worker.py`, `python -m app.agent.worker`, Compose service `chat_worker`) reads only the chat queue. One job (`app/agent/chat.py`): read the payload, load profile and memory, run the agent for the sender only, send with `send_answer` within the 24-hour window counted from the message's `received_at`, then store the exchange in Redis, `conversation_msg` and `user.language`. Nothing is stored after a deletion.
5. **Retries like the indexing worker**, before sending: `CHAT_RUN_DEADLINE_SECONDS` bounds the preparation; a model outage, the deadline, Redis or Postgres raise `arq.Retry` after `CHAT_RETRY_DELAY_SECONDS` × the try, up to `CHAT_MAX_TRIES`, and the last try sends the fixed error message in the user's language (English if it has no wording). A failure that would repeat sends the error message at once. Sending is never retried: right before it, the job marks the reply `sending` in `replies`, and a later try that finds that mark sends nothing (record 0011's rule that a possibly delivered message is not sent twice).
6. **Delivery and storing are tracked apart, in both stores.** The `sending` mark is written before sending with the exchange the answer adds: messages, working set, language, and a deletion question's request, planned then with its awaited message and a deadline counted from before sending. After a successful send, storing is tried up to `CHAT_MAX_TRIES` times in the run, `CHAT_RETRY_DELAY_SECONDS` × the attempt apart: first the `conversation_msg` rows (ids `uuid5(receipt, position)`, `ON CONFLICT DO NOTHING`; `user.language` only when the rows are new), then the `delivered` mark (one Redis script that changes only a reply still `sending`, so an erased reply stays erased), then, holding the user, the deletion request and the history and working set with the `stored` mark. Each store records the delivery on its own: a later try that finds a `delivered` mark, or a `sending` mark next to the exchange's rows, only stores, without running the agent or sending; the rows exist only after a send, so this never treats an uncertain send as delivered. A `sending` mark without rows still means "maybe sent", and nothing is sent again. The last try gives up and logs `chat_exchange_not_stored`.
7. **"Yes, delete" counts only on the next received message** (refines record 0015, point 10). `deletion_confirmed = confirms_deletion(message.quick_reply_payload)` as before, but "next" no longer depends on which job runs first. Ingestion gives every new message of a user, share or text, the next number, once per platform message id (`savely:ingestion:<user id>:messages`, a hash of each message's number and the last one), so a repeated delivery keeps its number and a new message re-sharing a post gets a new one; a share without a message id counts on every delivery. Right before the question is sent the worker reads the last number, and the delivered request waits for the one after it (`PendingDeletion.awaited_message`). Only the turn of that message takes the request (`take`, one atomic Redis script); a "no", a share or any other message in between uses it up, also when the tap's job runs first, is retried later or the tap is delivered twice. A typed "yes", an expired tap and another user's tap still delete nothing.
8. **"Delete my data" never races an answer.** The worker sends, and writes anything for the user (reply marks, the delivered request, history, working set, rows, language), only inside `ConversationStore.hold`: a transaction holding the user's row `FOR KEY SHARE`, and only if the user still exists. The erasure locks the same row `FOR UPDATE`, so it waits for an answer being sent or stored and then erases it, and an answer that gets there after the erasure is neither sent nor stored. `FOR KEY SHARE` doesn't block ingestion or the user's other answers. Only the "done" message is sent without the hold, to the recipients read before the erasure. `build_toolbox` gives `UserDataEraser` ingestion's state and jobs, the pending request, `SessionMemory` and the media store; `conversation_msg` rows and the profile go with the `user` row.

## Alternatives considered

- **One JSON value per user for the whole session**: simpler, but two answers ending together would lose one exchange.
- **Re-running the last search in code for a follow-up**: the model would no longer decide what "only the cheap ones" means; repeating the search with the arguments shown keeps the decision with the model and the checks with the tools.
- **A per-user lock around a whole turn**: would order concurrent messages, but the agent's tools take the user's row lock themselves, and a turn can wait for the model for a minute; the hold covers only sending and storing.
- **A separate "is the user still there?" check before sending or storing**: an erasure could still run between the check and the write; holding the row closes that gap.
- **Binding the question to the next message's receipt at ingestion**: needs ingestion to read and change the agent's request; a message number from ingestion and the number stored with the request do the same with one counter, and shares count too.
- **Storing the exchange only through the job's retries**: a Redis outage right after sending would leave no `delivered` mark, and the next try could only skip; trying again within the run, and keeping the planned exchange with the `sending` mark, lets either store carry it to the next try.
- **A new table for answers in progress**: would be a durable record of its own, but needs a migration; the `conversation_msg` rows already prove a delivery, and the rest of the exchange waits in the `sending` mark.
- **Storing the deletion request right after sending, outside the exchange**: a Redis failure there left a sent question that could never be confirmed; planning it before sending and storing it with the exchange keeps its awaited message and deadline whenever it is stored.
- **Reading the history from `conversation_msg`**: would not expire with the reply window, and costs a query per turn; Postgres keeps the record, Redis serves the turn.

## Consequences

- **Prompt version `2026-11-21.1`**: adds the profile line, the follow-up rules, `set_profile` and the working set's searches to `2026-11-20.3`. Like it, it is scored on the evaluation set when SAV-19/20 exist; there is no agent eval set yet, so there are no before/after numbers.
- **New settings:** `SESSION_TTL_SECONDS`, `SESSION_HISTORY_MESSAGES`, `CHAT_CONCURRENCY`, `CHAT_MAX_TRIES`, `CHAT_RETRY_DELAY_SECONDS`, `CHAT_RUN_DEADLINE_SECONDS`, `CHAT_JOB_TIMEOUT_SECONDS` (`ChatSettings`).
- **No schema change:** `user.home_area`, `user.country`, `user.language` and `conversation_msg` exist since migration 0001; the message counter is a Redis key, and the idempotent rows use the existing `conversation_msg.id`.
- **Limits:** messages of one user answered at the same time don't see each other in their history. A "Yes, delete" tap whose turn fails deletes nothing (the request was used up); the user asks again. A message that arrives while the question is being sent is the next one, so a typed message there uses the question up. A tap whose job runs before the question was recorded as delivered (the user tapped within the send call) deletes nothing. If both stores fail right after an answer was sent, the next try can't tell whether it arrived and keeps nothing, and if a store stays down for every try, the last one gives up. A deletion question whose request is stored only after the user already sent their next message can't be confirmed any more; the user asks again. `conversation_msg` keeps every exchange until "delete my data", with no expiry.
